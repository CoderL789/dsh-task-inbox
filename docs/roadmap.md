## Task 01：最小可运行独立插件

**状态：实现完成（待用户验收）**

**目标**：交付一个可以被 DSH 官方插件管理器安装、加载的独立插件包，并在界面上提供「Task Inbox」侧边栏入口与独立页面（仅插件名称 +「暂无待办」空状态）。不包含任何待办业务能力与 Agent 执行能力。

**交付物**：

- 插件包骨架：包清单（`package.json`）、Cordis bundle patch（`cordis.patch.yml`）、`tsconfig.json`、插件图标（`icon.svg`）、locale 目录（`en.json` / `zh.json`，插件元信息）；
- TypeScript 源码经构建输出为 JS（`lib/`）；
- Host 半区：插件挂载点，`apply` 为空，不注册业务逻辑；
- Client 半区：在 Harness 侧边栏注册「Task Inbox」（中文界面为「待办箱」）入口，点击打开独立页面，展示插件名称、简介与「暂无待办」空状态；当前页面文案已内置 zh / en 两种语言；
- 文档：`README.md`、`docs/roadmap.md`、`docs/api-notes.md`（API 调研笔记）；
- 仓库基础文件：`LICENSE`（MIT）、`.gitignore`。

**验收标准**：

1. 通过 DSH 官方插件管理器以本地 bundle 方式（`install_bundle`，目标为插件包目录的绝对路径）安装到桌面测试 profile；
2. 安装后侧边栏出现「Task Inbox」入口，点击可打开独立页面；
3. 页面正确展示插件名称与「暂无待办」空状态，无脚本报错导致的白屏；
4. 构建可重复执行：从干净依赖安装后运行构建，产物完整；
5. 文档与实现一致，不包含未实现能力的宣称；
6. 卸载（`remove_bundle`）后插件入口消失，不残留持久化数据。

**风险**：

- bundle patch 结构与当前 DSH 版本期望不一致，导致安装成功但插件未挂载；
- 侧边栏入口 / 页面注册能力在不同 DSH 版本间存在差异，可能需要按版本调整；
- 桌面测试 profile 的安装环境与目标 profile 存在差异，验收结论不能直接推广；
- 文档撰写先于实现细节固化，存在描述与最终实现偏差的风险，需在验收后校对。

## Task 02：待办数据模型与持久化 + CRUD 界面

**状态：待开始**

**目标**：建立「待办归属于插件」的核心能力——待办可创建、编辑、完成、删除，并在跨会话、跨重启后依然存在。此阶段仍不执行待办。

**交付物**：

- 待办数据模型（字段、状态、时间戳等）与校验规则；
- Host 侧待办存储与读写服务（增删改查），以及持久化落盘方案；
- Client 侧待办箱界面：列表、创建、编辑、完成、删除、空状态与基础筛选；
- 与 persisted 数据一致的 locale 文案；
- 文档更新：数据模型说明、数据位置与备份 / 卸载说明。

**验收标准**：

1. 不依赖任何会话即可创建与管理待办；
2. 重启 DSH 后待办完整保留，顺序与状态一致；
3. 增删改查操作在界面上可用，非法输入有校验提示；
4. 空列表展示「暂无待办」状态，与 Task 01 的占位状态自然衔接；
5. 数据损坏或缺失时可恢复 / 提示，不会导致插件崩溃。

**风险**：

- 持久化选型（Host 侧文件、profile 存储或插件配置）尚未定案，影响数据位置、备份与升级迁移；
- 并发写入与多会话同时操作时的数据一致性；
- 数据目录权限与跨平台路径差异（Windows / macOS / Linux）。

## Task 03：工作区 / 会话选择与执行派发

**状态：待开始**

**目标**：待办从「收集」走向「执行」。用户执行待办时先选择工作区，再决定会话策略：新建会话、复用已有会话，或从已有会话 Fork 出新会话，然后交给 Agent 执行。

**交付物**：

- 执行前的配置界面：工作区选择、会话策略选择（新建 / 复用 / Fork）、必要的确认步骤；
- Host 侧派发逻辑：按策略创建 / 复用 / Fork 会话，并把待办内容提交给 Agent；
- 待办与会话的绑定记录（哪个待办绑定了哪个会话、哪一种策略、何时）；
- 失败处理：工作区不可用、会话创建失败、策略不被支持时的降级与提示；
- 文档更新：执行流程与策略说明、已知限制。

**验收标准**：

1. 三种策略均可完成一次真实执行，Agent 在所选工作区内工作；
2. 复用已有会话时，待办内容正确进入该会话上下文；
3. Fork 策略从所选会话分出独立新会话，原会话不受影响；
4. 待办与执行会话的绑定关系可查询，重复执行有明确记录；
5. 任一策略失败时不丢失待办，用户可重试或更换策略。

**风险**：

- 会话创建 / 复用 / Fork 与派发的 API 形态与稳定性在 DSH 中尚未最终确认（见 [api-notes.md](api-notes.md)），若官方接口调整需重做派发层；
- 工作区句柄在不同入口 / 版本下可能不可得，影响策略可选范围；
- 权限与审批边界：派发属于会触发 Agent 行为的操作，需符合 DSH 的权限模型；
- 上下文过大时（复用已有会话），待办内容可能被稀释或截断，需设计提示与确认。

## Task 04：执行追踪

**状态：待开始**

**目标**：把「执行」当作一等对象追踪：记录状态（待执行 / 执行中 / 成功 / 失败 / 取消）、历史、绑定的会话与工作区，并提供结果关联与回溯入口。

**交付物**：

- 执行记录模型与生命周期状态机；
- Host 侧执行状态跟踪与持久化；
- Client 侧界面：执行状态展示、执行历史列表、从执行记录跳转到对应会话 / 结果；
- 异常恢复：DSH 重启或崩溃后，对孤儿执行（会话已不存在或状态不明）的处理与标记；
- 文档更新：状态语义与排查方法。

**验收标准**：

1. 执行状态在界面上能实时反映（至少在执行开始与结束时正确更新）；
2. 历史列表按时间排序，可回溯每次执行绑定的会话、工作区与结果摘要；
3. 重启后执行记录与状态保持一致，孤立记录被明确标记而不静默丢失；
4. 失败 / 取消有明确状态与原因，可从记录中查看；
5. 从历史记录可跳转到对应会话（若能力可用）。

**风险**：

- 执行状态依赖 Agent 会话的事件 / 结果能力，接口稳定性与事件粒度为最大不确定项；
- 崩溃与重启后的状态对齐（孤儿执行判定）复杂度较高；
- 结果摘要的获取与展示可能超出当前 DSH 暴露的能力范围，需要降级方案；
- 状态机若不严谨，易出现状态卡死或错误终态。

## Task 05：打磨与开源发布准备

**状态：待开始**

**目标**：完成国际化、可访问性、打包与开源发布所需事项，使插件具备对外发布的质量与流程。

**交付物**：

- 完整国际化：`en` / `zh` 文案覆盖全部界面与提示；
- 可访问性：键盘导航、焦点管理、语义标签与对比度检查；
- 打包与发布准备：安装包内容校验（含构建产物与必要文件）、版本策略、发布说明（Changelog / Release Notes）；
- 开源就绪：README、LICENSE、路线图与文档最终校对，贡献指南与发布渠道确定；
- 质量：关键流程的人工验收清单，必要时补自动化测试。

**验收标准**：

1. 两种语言界面完整可切换，无遗漏硬编码文案；
2. 纯键盘可完成待办创建、执行与查看历史等核心流程；
3. 以官方插件管理器安装发布包可复现成功，卸载干净；
4. 仓库文档与实现一致，无编造的 URL、徽章或 API；
5. 发布前完成一轮人工验收并记录结果。

**风险**：

- 国际化接入方式已在 Task 01 初步验证（Client locale 服务），但完整覆盖范围与 `locale/*.json` 的最终用途仍待确认，成本未定；
- 视觉与交互质量目前依赖人工验收，缺少自动化视觉回归手段；
- 发布流程与包名 / 版本策略需要维护者决策，可能影响文档与安装说明；
- 发布前若上游 DSH 版本对插件接口有破坏性变更，需额外适配时间。
